# ADR-018: 中断した会議を通常の履歴として扱う

- **Status**: Accepted
- **Date**: 2026-10-01
- **Supersession**: ADR-003 の中断会議の管理方針と、ADR-016 の Rust 直接接続における復旧待ち方針を部分置換する。
- **Partially superseded by**: [ADR-022](./022-rust-backend-authority.md)（Python バックエンドと移行用 adapter が別 lifecycle として残る前提。本文は判断当時の記録として保持する）

## Context

認識結果の欠落、保存失敗、子プロセスの停止失敗は異なる障害である。
これらを一律に未確定会議として残すと、保存済みの記録があっても削除できず、
次の会議のために再起動が必要になる。利用者が内部の整合性を判断する復旧画面は設けない。

## Decision

### 記録の完全性と実行資源の状態を分ける

Rust の直接接続では、会議の結果を次のように扱う。

| 状況 | 記録と表示 | 次の会議 |
|---|---|---|
| 正常終了 | `completed` として保存し、保存完了を通知する。 | 開始できる。 |
| 認識・取得・録音の中断 | 保存できた発言と利用可能な録音を残し、`aborted` として履歴に表示する。欠落の可能性を案内する。 | 処理の停止・回収と保存先の書き込みを確認できれば開始できる。 |
| 保存失敗 | 一部未保存であることを明示し、保存済みの内容と残ったファイルを保持する。中断状態すら保存できない場合は `active` が残り得る。 | 保存先が再び書き込み可能になってから開始できる。 |
| 停止・回収を確認できない | 会議を正常完了と通知せず、再起動を案内する。 | 同じ実行資源を再利用しない。 |

終了操作では入力を切り離し、認識の残りを期限内で待ち、録音を確定する。
障害時は子プロセスと結果受信タスクの終了を確認してから中断状態を保存する。
認識の失敗だけを理由に保存済みの発言や取得済みの録音を削除しない。
正常に終了しなかった会議へ新しい発言を追記する再開機能は設けない。

保存できなかった本文を再試行できると装わない。再試行はデータが保持され、
重複保存を防げる場合だけ提供する。現在の直接接続は未保存本文の再送キューを持たず、
保存失敗を通知する。録音からの再認識と破損ファイルの修復は別の機能とする。

### 起動時に残った会議を整理する

Rust runtime は保存先の排他ロックを保持する。他の Rust runtime が所有している保存先は開かない。
起動時と次の会議を開始する前に、実行中の会議がないことを前提として、残った `active` を `aborted` にする。
書き込みに失敗した場合は新しい会議を開始しない。クラッシュの終了時刻や長さは推測しない。

既存の発言・返答・資料・録音情報は保持する。録音情報が欠けている場合は、
アプリの録音ディレクトリにある確定済みの 16 kHz・モノラル・16 bit PCM WAV を検証し、
利用可能な録音として登録する。シンボリックリンクを辿らず、音声本文を変更しない。
未確定・破損した WAV は再生可能と表示せず、ファイルを保持する。
同じ整理を繰り返しても録音情報を重複させない。

### 専用の復旧画面を作らない

開始画面では中断、一部未保存、停止確認失敗を区別し、履歴への導線を表示する。
`meeting_state.end_status` は Rust が確定した終了結果を表し、UI はエラーメッセージから推測しない。
履歴では `aborted` を「中断」と表示し、文字起こしや録音の欠落の可能性を案内する。
保存済みの内容を閲覧でき、通常の確認ダイアログから会議と関連ファイルを削除できる。
実際に実行中・終了処理中の会議、停止を確認できない会議は削除しない。
期限・容量による一括整理は引き続き `completed` だけを対象とする。

## Rejected Alternatives

- 利用者が「復旧」か「破棄」かを必ず選ぶ画面: 保存やプロセスの状態を利用者に判断させることになる。
- 障害後はすべて `active` のまま保持する: 終了と欠落を混同し、通常の履歴管理を妨げる。
- 残った会議をすべて `completed` にする: 欠落や保存失敗を正常完了として通知してしまう。
- 録音を自動修復・再認識する: この判断では扱わない追加処理であり、取得できなかった音声は復元できない。

## Consequences

中断した記録を通常の履歴で扱え、認識障害から次の会議へ進める。
既存の SQLite 状態を使用するためスキーマ変更は不要である。
`aborted` の表示は欠落の可能性を示すもので、欠落区間の特定や全データの復元を保証しない。
録音ファイルの検証や停止確認に失敗した場合の制約は残る。
Python バックエンドと移行用 Python アダプターの lifecycle はこの変更の対象外である。
