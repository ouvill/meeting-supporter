# Rust 音声コアの試作

Rust 音声ワーカーが利用する、発話区間の切り出しと認識入力の準備を担当するライブラリです。
標準アプリの起動・配布は [Rust バックエンド](../../doc/development/rust-desktop-backend.md)を参照してください。

## 実装と互換性

[src/lib.rs](src/lib.rs) の `Segmenter::push` に 16 kHz・mono・PCM16LE の 30 ms フレームと VAD 判定を渡します。完成した `Segment` には正規化した音声、発話フレーム数、RMS、認識可否を含めています。話者ごとに独立したインスタンスを作ります。

- 発話前の 5 フレーム（150 ms）を認識入力に含めます。入力判定の RMS・発話比率には含めません。
- 無音閾値または 934 フレームで区切ります。前置音声とモデル側の前後パディングを含めても 30 秒未満です。
- `finish()` は Python の終端 sentinel に対応します。キャンセル時は flush せずインスタンスを破棄します。新しい会議には新しいインスタンスが必要です。
- フレーム長、VAD フラグ、有限の設定値を検証します。ライブラリは音声全体を保持せず、最大区間と前置音声だけをバッファします。
- 音声サンプルは比較ケースで完全一致しました。ただし Rust の RMS 累積は `f64`、Python の NumPy dot は `float32` です。閾値に極めて近い入力では採否が異なる可能性があり、完全互換とはみなしません。
- デバイス取得、VAD 推論、文字起こし、UI の途中状態通知、キューのあふれ、タイムスタンプ欠落、スレッド停止、保存は試作の対象外です。

音声ワーカーがこのライブラリを直接呼びます。CLI は単体リプレイ用で、ライブ配信のプロトコルや障害回復を定義しません。

## 測定結果

2026-09-29、参照コード `51b65e1`、Linux x86_64、Rust 1.98.1 release、Python 3.14.4、NumPy 2.4.4 で測定しました。各入力は 10,000 フレーム（5 分相当、1 話者）で、ウォームアップ後 7 回の中央値です。音声を実時間より速く流しています。CPU を占有した単独ベンチマーク環境ではなく、この環境での参考値です。

| 合成入力 | Python stage | Rust core | Rust 起動・パイプ I/O 込み |
|---|---:|---:|---:|
| 無音 | 7.69 ms | 0.47 ms | 16.25 ms |
| 発話 70・無音 30 フレームの繰り返し | 11.77 ms | 4.30 ms | 19.23 ms |
| 連続発話 | 11.60 ms | 6.15 ms | 32.91 ms |

Python の計時範囲は Queue 取り出し、状態管理、NumPy 変換、途中通知の生成、出力収集です。Rust core は `push` / `finish` の時間を合計し、フレームごとの時計計測を含みます。CLI 起動と読み書きは除外します。Rust の最終列はプロセス起動・音声の送受信を含み、Python 側での出力解析は含みません。入力生成・Python の import・キュー充填は計測外です。

比較する層が異なるため、比率を Rust 言語そのものの優位性やアプリ全体の高速化率とは解釈できません。今回の発話・無音ケースではコアの差は 5 分あたり約 7.5 ms、1 フレーム平均で約 0.75 µs でした。プロセス境界を足すと逆に遅くなりました。

## CLI の実験用形式

引数は省略時に既定値を使い、指定時は `silence_seconds min_voiced_ms min_voiced_ratio min_rms_dbfs` の 4 個です。

標準入力は `VAD u8 (0/1)` と `PCM16LE 960 bytes` の連続です。EOF で残りの区間を確定します。標準出力には採用区間だけを `終端フレーム番号 u64 LE`、`サンプル数 u32 LE`、`float32 LE × サンプル数` の順に出します。フレーム番号は 0 始まりで、EOF flush は入力フレーム数です。標準エラーには成功時のコア処理時間（ns）を出します。入力不正や I/O エラーでは非ゼロ終了します。途中まで出力される場合があるため、呼び出し側は終了コードを必ず確認します。
